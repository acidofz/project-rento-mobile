# RENTO — мобильный клиент

Клиент для P2P-аренды жилья в **Ташкенте** (Узбекистан): объявления, избранное, чаты, профиль. Интерфейс по умолчанию на **русском**. Бэкенд — **Supabase** (Auth, Postgres, RLS, Storage, Realtime).

## Связь с веб-проектом

| Ресурс | Ссылка |
|--------|--------|
| Репозиторий веб-приложения | [github.com/acidofz/project-rento](https://github.com/acidofz/project-rento) |
| Продакшен (Railway) | [project-rento-production.up.railway.app](https://project-rento-production.up.railway.app) |

Схема таблиц и политик RLS в репозитории: `supabase_schema.sql` (согласуйте с миграциями веб-проекта при изменениях).

## Стек (основная ветка репозитория)

- **Expo SDK 54** + **React Native** + **TypeScript**
- **expo-router** — файловая навигация
- **@supabase/supabase-js** — сессия в SecureStore (на вебе в разработке — `localStorage`)

## Быстрый старт

```bash
cp .env.example .env
# EXPO_PUBLIC_SUPABASE_URL и EXPO_PUBLIC_SUPABASE_ANON_KEY из Supabase → Settings → API
npm install
npx expo start
```

Дальше: эмулятор/устройство (**Android** / **iOS**) или веб для отладки UI.

## Цель и паритет с веб-MVP

Продукт — **P2P-аренда жилья в Ташкенте**: лента, карточка объявления, избранное, **свои** объявления (CRUD + обложка в Storage), чаты, профиль, статические «Правила» и «Персональные данные». Бэкенд только **Supabase**; тексты интерфейса по умолчанию **короткие, на русском**. Админка в приложении не планируется.

Цель мобильного клиента — **паритет с веб-MVP** по сценариям и данным; имена таблиц/полей и RLS — как в `supabase_schema.sql` и в веб-репозитории.

## План разработки (фазы)

### Фаза 1 — Объявления «до конца»

- Список **своих** объявлений (`owner_id`), **создание / редактирование / удаление**; поля как на вебе.
- Загрузка обложки в бакет **`listing-images`**, путь **`{user_id}/...`** под RLS; сохранение `image_url`; опционально `latitude` / `longitude` для карты.
- Для **`is_blocked`**: скрыть или явно отключить создание объявлений и чат (как договоритесь с вебом).

### Фаза 2 — Избранное

- Таблица `favorites`: переключатель на карточке/в детали, список на вкладке, пустые состояния.
- Для гостя: CTA «Войти» или только просмотр без записи в БД.

### Фаза 3 — Чаты

- Старт с объявления: в схеме репозитория — RPC **`find_or_create_peer_chat(peer_id)`** (диалог 1:1 без `listing_id` на чате); **выложите SQL на Supabase** и согласуйте то же на вебе.
- Чтение **`chat_members`**: политика SELECT использует **`current_user_chat_ids()`** (`SECURITY DEFINER`), иначе подзапрос к той же таблице даёт рекурсию RLS.
- Список диалогов, переписка, отправка текста.
- **Supabase Realtime** по `messages`: хук `useChatMessagesRealtime`, JWT через `realtime.setAuth` при смене сессии; публикация таблицы `messages` для `supabase_realtime` — SQL в конце `supabase_schema.sql`. Если канал не подписался — опрос чаще (7 с), после подписки — реже (45 с).

### Фаза 4 — Карта

- В клиенте: **`components/map/MapTabContent.native.tsx`** + **react-native-maps** (только iOS/Android); **`MapTabContent.tsx`** — список с координатами для веба; маршрут `app/(tabs)/map.tsx` только реэкспортирует контент.
- Согласовать с вебом список полей и обязательность координат при подаче объявления.

### Фаза 5 — Полировка и публикация

- В клиенте: расширенные сообщения для сети / сессии / RLS в `mapQueryError`; правовые экраны через **WebView** с продакшен-URL + черновик при ошибке; **EAS** — файл `eas.json`, идентификаторы в `app.json`.
- Онбординг по необходимости — не делался; пустые состояния — по экранам (лента, избранное, чаты, карта).
- Перед релизом: **`eas init`**, иконки/splash, **секреты в EAS** (не в git); для **Android** при необходимости ключ **Google Maps** в конфиге сборки; формы **Privacy / Data safety** в консолях сторов и финальный текст с юристом.

### Фаза 6 — После MVP (опционально)

Пуш-уведомления, deep link на объявление, кэш ленты офлайн, метрики, локализация uz.

## Риски и зависимости

- **Веб-репозиторий** — источник правды по запросам, сортировкам и UX; при расхождении сначала править контракт, потом клиенты.
- **Чат от лота** — без общей модели с вебом легко получить дубли чатов или нарушение RLS.
- **Realtime** — в проекте должна быть настроена публикация для нужных таблиц в Supabase; иначе закладываться на polling.

## Критерий готовности MVP к сторам

Лента с фильтрами и деталью; **свои** объявления с фото в Storage; избранное; чаты с отправкой текста; карта с маркерами; профиль и корректная обработка блокировки; статические правовые экраны; **сборки iOS и Android через EAS**; заполненные формы приватности в консолях App Store и Google Play.

## Сборка для магазинов

**iOS и Android:** [EAS Build](https://docs.expo.dev/build/introduction/) из корня проекта; секреты и ключи — в EAS, не в git.

Черновой порядок: установить [EAS CLI](https://docs.expo.dev/build/setup/), выполнить `eas login` и **`eas init`** (создаст/привяжет проект в expo.dev). Сборки: `eas build --profile development|preview|production` для нужной платформы (`--platform ios|android|all`). Перед продакшеном замените при необходимости **`com.rento.mobile`** в `app.json` на свой идентификатор организации; для карт на Android в релизе может понадобиться ключ Google Maps (см. документацию `react-native-maps` и Expo).
